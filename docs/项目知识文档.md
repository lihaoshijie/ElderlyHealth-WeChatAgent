# MyDemo Bot 项目文档

> 更新日期：2026-08-01

## 一、项目概述

基于 Spring Boot + MyBatis + LangChain4j，集成 iLink SDK，实现微信智能助手 Bot。支持 60+ 内置工具 + 12306 MCP 工具 + B站收藏夹集成。**全部由 LLM Function Calling + @Tool 注解驱动，零硬编码关键词匹配。**

## 四、核心架构

### 4.1 Agent Loop（ReAct 循环）

Agent Loop 是整个机器人的"大脑循环"，位于 `CommandRouter.route()` 中，负责调度 LLM 与工具之间的多轮交互。

#### 流程图

```
用户消息 "明天杭州天气怎么样"
    │
    ▼
[1] ToolRegistry.filterToolsByInput("明天杭州天气怎么样")
    → 匹配域: 天气, 时间 → 只发 6 个工具（而不是全部 82 个）
    │
    ▼
[2] LlmService.chatRaw(消息, 过滤后工具)
    → LLM 判断: 需要调 weather + local_time
    → 返回 function_call: [{weather, city:"杭州"}, {local_time}]
    │
    ▼
[3] 工具执行（≤1 个工具同步，≥2 个 CompletableFuture 并行）
    ├── weather("杭州") → "杭州 晴天 28°C"
    └── local_time()   → "2026-08-01 10:30 周五"
    │
    ▼
[4] 结果回填 messages（超长截断保护）
    → LlmService.chatRaw(消息 + 工具结果, 工具)
    │
    ▼
[5] LLM 综合生成长自然语言回复
    → "杭州明天晴天，28°C，适合出行"
```

#### 关键机制

| 机制 | 实现 | 说明 |
|------|------|------|
| 动态工具分域 | `ToolRegistry.filterToolsByInput()` | 关键词匹配，闲聊只发 5 个通用工具 |
| 并行工具执行 | `CompletableFuture.runAsync` | 同轮多个工具并发，5s→2s |
| Token 预算保护 | `tokensUsed > TOKEN_BUDGET` (100K) | 超额强总结，不炸上下文 |
| 超时保护 | `elapsed > TOTAL_TIMEOUT_MS` (90s) | 超时强总结，不死循环 |
| 工具结果截断 | `truncateToolResult()` (10000字) | 字幕/文件不撑爆多轮上下文 |
| 去重拦截 | `calledKeys` 集合 | 同工具+同参数不准重复调 |
| 降级重试 | `autoDegrade()` | 百度→Google 互切 |
| 最大轮次 | `MAX_TOOL_ROUNDS = 3` | 上限 3 轮，防止无限循环 |
| selfCheck | 回复含"可能/也许"时自检 | 可配置触发条件 |

### 4.2 Skill 系统

Skill 是工具被调用时自动激活的行为规则，用于引导 LLM 按正确模式使用工具组合。不同于 System Prompt 的静态规则，Skill 是**按需注入**的——只有工具被实际调用后才激活。

#### 工作机制

```
CommandRouter 执行工具
    │
    ▼
skillManager.getSkillsFor(call.name())
    → 检查该工具绑定了哪些 Skill
    │
    ▼
如果 Skill 尚未激活 → 加入 activeSkills
    │
    ▼
下一轮 LLM 请求时 → injectSkills()
    → 将 Skill 规则注入 System Prompt
```

#### 已有 Skill（13 个）

| Skill | 触发工具 | 规则摘要 |
|-------|---------|---------|
| 搜索 | baidu_search, google_search | 搜到网址调 qr_code；搜到品牌查当地时间 |
| 天气 | weather, air_quality | 并行查天气+空气质量；emoji 美化 |
| 旅游 | search_poi, generate_travel_plan | 查景点→生成攻略→原样发给用户，不压缩改写 |
| 图片 | generate_image, transform_image | 生成后不在文字中重复描述 |
| 文件 | translate_file, extract_from_file | 结果以 TXT 返回；完成后提示导出 |
| 热搜 | network_hot, ai_news | 追问详情时调 ai_news，不编造内容 |
| 健康饮食 | body_fat_rate, food_nutrition | 查食物同时调营养+健康建议 |
| 待办提醒 | add_todo, create_reminder | 增删后自动 list 确认 |
| 语音 | enable_voice, switch_voice | 用完自动关，不主动开 |
| 生日命理 | eight_characters, annual_fortune | 并行排盘+流年+五行+日历 |
| 快递 | query_delivery | 中通/申通必须手机尾号；emoji 标注状态 |
| 记忆 | remember_fact | 用户透露个人信息时主动保存 |

*注：麦当劳 MCP Skill 已随相关代码移除。*

#### 添加新 Skill

```java
@Component
public class YourSkill implements Skill {
    public String getName() { return "你的技能"; }
    public String getRule() { return "行为规则文本"; }
    public List<String> getTools() { return List.of("tool_name"); }
}
```

#### 与 System Prompt 的区别

| | System Prompt | Skill |
|:--|:--|:--|
| 注入时机 | 每次请求 | 工具调用后才注入 |
| Token 成本 | 始终占用 | 仅触发时占用 |
| 适用场景 | 全局行为规范 | 工具组合使用规范 |
| 修改方式 | 改 application.yaml | 新增/修改 Java 类 |

### 4.3 RAG 检索系统

RAG（Retrieval-Augmented Generation）让 Bot 能回答基于上传文档的问题。文档内容被切块→向量化→存入 MySQL，用户提问时检索相关块注入上下文。

#### 两条管线

```
当前（RagService）                  新管线（RagPipelineService，待接入）
┌────────────────────┐              ┌──────────────────────────────┐
│ 空库预检→embedding  │              │ 闲聊短路→预检(0.45)→单路混合   │
│ →全文/全表→cosine  │              │ 检索→注入(限1500字)           │
│ →注入              │              │ 省 embedding + 省改写耗时      │
│ CommandRouter 调   │              │ 待从 Route 变更入口           │
└────────────────────┘              └──────────────────────────────┘
```

#### RAG 新管线详解

```
用户提问 "蜈支洲岛门票多少钱"
    │
    ▼
[1] isChat("蜈支洲岛门票多少钱") → 否，不是闲聊
    │
    ▼
[2] maxSimilarity(query, 全库向量) → 0.582 > 阈值 0.45 → 通过预检
    │
    ▼
[3] searchDirect(query): 向量检索(0.6) + BM25(0.4) → 相关文档块
    │
    ▼
[4] 注入: 单块≤500字, 总量≤1500字 → 拼入 System Prompt
    │
    ▼
[5] LLM 基于文档回答: "蜈支洲岛门票 144 元"
```

#### 关键机制

| 机制 | 实现 | 效果 |
|------|------|------|
| 闲聊短路 | `isChat()` 规则匹配 | "你好"不跑检索 |
| 预检拦截 | `maxSimilarity < 0.45` 跳过 | 知识库外问题直接拦截 |
| TTL 缓存 | 60s 内免查 DB | 重复问题秒回 |
| 向量缓存 | `embedCache` 内存 Map | 同查询不重复调 API |
| 注入限长 | 单块 500 字 / 总量 1500 字 | 上下文不膨胀 |
| 空库跳过 | `SELECT COUNT(*)` 预检 | 无文档时不调 embedding |

#### 文档入库流程

```
用户上传文件 → WeChatBotService.handleFileMessage()
    │
    ▼
ragService.ingestDocument(bytes, fileName)
    │
    ├── DocumentService.extractText()  提取文本
    ├── DocumentService.splitText()    切块（1000字/100字重叠）
    ├── EmbeddingService.embed()       每块向量化（DashScope API）
    └── INSERT INTO doc_embeddings     存入 MySQL

### 4.4 MCP 外部工具接入

MCP（Model Context Protocol）是通过标准协议接入外部工具服务的机制。项目支持两种模式：

#### stdio 模式（12306 火车票）

```
McpIntegration.init()  ← @PostConstruct
    │
    ├── ProcessBuilder("npx", "12306-mcp")  启动 Node 子进程
    ├── 通过 stdin/stdout 发送 JSON-RPC
    │
    ├── initialize → {"jsonrpc":"2.0","method":"initialize"}
    ├── tools/list → 获取 12306 提供的工具清单
    │
    ├── 逐工具解析 name/description/inputSchema
    └── ToolRegistry.registerExternal(name, toolFunction, executor)
```

调用时：`tools/call → JSON-RPC → 子进程 → 返回结果 → 回填 LLM`

#### HTTP 模式（预留）

通过 HTTP POST JSON-RPC 调用远程 MCP 服务器，适用于无需本地子进程的外部服务。

#### 与 @Tool 的协作

MCP 工具通过 `registerExternal()` 注册到 ToolRegistry，与本地 `@Tool` 共用统一接口：
- 本地工具：反射调用 @Tool 方法
- 外部工具：`executor.apply(toolName, args, userId)` 走 MCP 通道

**注意**：MCP 工具名运行时确定，工具分域的 DOMAIN_TOOLS 列表无法硬编码——已做特殊处理，12306/B站域命中时不过滤，返回全部工具。

### 4.5 工具注册与反射执行

ToolRegistry 是工具系统的核心，负责发现、注册、过滤、执行全部工具。

#### 扫描机制

```
ToolRegistry.init()  ← @PostConstruct
    │
    ├── 遍历 Spring 容器所有 Bean 的 @Tool 方法
    ├── 提取 @Tool.name(工具名) / @Tool.value(描述) / @P(参数)
    ├── 构建 JSON Schema（自动过滤 userId 等系统参数）
    ├── 同名工具跳过（WARN 日志）
    └── 存入 Map<String, ToolEntry> → buildTools() 缓存
```

#### 执行流程

```
ToolRegistry.execute(toolName, args, userId)
    │
    ├── 查 ToolEntry
    │   ├── 有 executor → 外部工具（MCP 等）
    │   └── 无 executor → 反射执行 @Tool 方法
    │       ├── JSON 反序列化 args → 参数列表
    │       ├── systemParam 自动注入 userId
    │       └── method.invoke(bean, callArgs) → String
    │
    └── 返回结果字符串
```

#### 工具类型

| 类型 | 注册方式 | 执行方式 |
|------|---------|---------|
| @Tool 本地工具 | `@PostConstruct` 扫描 | 反射调用 |
| MCP 外部工具 | `registerExternal()` | executor 回调 |
| MCP（12306） | McpIntegration 启动时 | JSON-RPC over stdio |

### 4.7 事件机制（ToolExecutionContext）

`@Tool` 方法产生"副作用"（生成图片、存文件、发语音）时，不能直接从工具方法内执行——需要通过 ThreadLocal 事件队列延迟到 `sendReply()` 阶段统一处理。

#### 工作原理

```
@Tool 方法                            sendReply()
   │                                      │
   ├── recordImageGen() → 记录事件  →     ├── doImageGen() 发送图片
   ├── recordFileTranslate() →        →   ├── doFileToolAction() 发文件
   ├── recordQrCode() →              →    ├── doQrCodeGen() 发二维码
   └── recordReExamine() →          →     └── doReExamine() 重识别

事件存储：ThreadLocal<PendingAction>
生命周期：handleMessage() 入口清空 → sendReply() 消费后 clear
```

**为什么不用 @Tool 直接发？** @Tool 方法的返回值会拼入 LLM 上下文，如果图片/文件在工具内直接发，返回值和实际发送的内容会不一致，导致 LLM 的后续回复混乱。

### 4.8 对话历史管理（ChatService）

ChatService 负责多轮对话的持久化和 Token 预算控制。

#### 压缩策略

```
addHistory(userId, msg) → saveHistory(userId, history)
    │
    ├── estimateTokens(history)  ← 粗估（字符数/1.5）
    │
    ├── 超过阈值 → 调用 LLM 摘取对话摘要
    │   └── 保留最近消息 + 摘要 → 存入 MySQL
    │
    └── 异步落库：dbWriter.submit(() → MySQL insert)
```

#### 存储结构

| 组件 | 存储 | 说明 |
|------|------|------|
| 对话历史 | MySQL `chat_history` 表 | user_id + JSON content |
| 用户信息 | MySQL `admin_user_info` 表 | 首次联系时间、消息计数 |
| 消息记录 | MySQL `admin_user_messages` 表 | role + content 逐条存储 |
